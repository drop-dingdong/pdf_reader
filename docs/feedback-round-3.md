## §18 800% 仍旧黑屏 —— 已排查到后端之外，需要你的一段诊断输出 🔍

### 已经排除的可能（都有测试，不是推测）

本轮为这件事补了 **3 条真实 PDFium 测试**，全部通过：

| 测试 | 结论 |
| --- | --- |
| `every_tile_contains_ink_for_a_full_page_document` | 800%（网格 10×13）下**每一块瓦片都有墨**，不是空白 |
| `tiles_match_the_crop_of_the_whole_page_render` | 瓦片与"整页渲染后裁出的同一区域"**逐像素一致**（±16）→ 分块几何完全正确 |
| `tiles_at_800_percent_still_contain_ink` | 800% 下瓦片渲染**每块约 9ms**、尺寸正确（含越界余数块 288×192） |

同时也验证过：`visible_tiles` 的瓦片范围、`PagePlacement::pixel_size()`、`Scale::is_valid()`、
`Rect::intersects` 在 800% 下都正常；`MAX_ZOOM = 8.0`，正好是你测到的上限。

**结论**：后端渲染、分块几何、坐标换算都不是原因 —— 问题只可能在
"app 每帧的绘制决策"或"真实 GPU 的纹理上传"上，而这两件事都**无法在无头环境复现**。

### 因此本轮加了运行时诊断输出

```bash
PDF_READER_DIAGNOSE=1 cargo run -p app -- <你的PDF>
# 复现黑屏后，把 stderr 里的 [诊断] 行贴给我
```

每行包含：缩放、视口尺寸、scroll、当前页、可见页、纹理数、在飞任务数、
`max_texture_side`，以及**每一页实际走的画法**（整页纹理 / 旧图拉伸 / 瓦片 n/m / 白底页框）。

有了这几行就能立刻定位：

* 若显示"**画法=瓦片 0/6**" → 瓦片没进纹理（渲染或上传环节）；
* 若显示"画法=瓦片 6/6"却仍然黑 → 纹理上传成功但 GPU 端无效（`max_texture_side` 就是线索）；
* 若**没有任何行**包含该页 → 可见页计算为空（布局/滚动状态问题）；
* 若"画法=旧图拉伸"或"白底页框" → 走的是占位路径，说明新比例的位图始终没到。

### 同时做的两处稳健性改动

1. **分块阈值降到 4 MP（D-15）**：800% 时绝大多数页面会走分块路径，
   单张纹理只有 512×512，彻底避开"大纹理在真实 GPU 上失败"这一类问题；
2. **取消过时在飞任务（D-16）**：缩放过程中不再堆积旧的渲染任务，
   这也直接改善你说的"放大缩小总是有顿感"。
