# 深度缩放的两条路线：预览质量阶梯 与 视口空间渲染

> 用户提问记录（第五轮之后）。本文说明两者的动机、机制、与现状的差距、代价，
> 以及**为什么"分块渲染"已经把一部分收益提前拿到了**。

---

## 0. 现状：请求模型与成本公式

一条渲染请求是**页面空间**的（`pdfcore::render::RenderRequest`）：

```rust
RenderRequest { page, scale, rotation, tile: Option<TileSpec> }
```

* `scale` 的单位是 **像素 / PDF 点**（`Scale::from_zoom(8.0)` = 8 px/pt）；
* 内容空间定义：1 内容单位 = 1 PDF 点 × 缩放，所以**当前缩放下 1 内容单位恰好等于 1 位图像素**（D-17 的不变量）。

因此"整页位图"的像素数是：

```text
宽 × 高 = (页点数 × 缩放)²  →  成本随缩放的**平方**增长
612×792 pt @ 800%  →  4896×6336 = 31.0 MP = 124 MB（BGRA，另有等量的 RGBA 转换缓冲）
```

已有的三层缓解（都不是本文两条路线，但已经把成本压下来了）：

| 机制 | 作用 | 效果（真实实测） |
| --- | --- | --- |
| **分块渲染**（`TILE_SIZE = 512`，阈值 4 MP，D-15） | 只渲染视口覆盖到的瓦片 | 视口 513×576 时 **6 块**，约 1.6 MP（6 MB）而不是 124 MB；单块实测 **~9ms** |
| **预取 ±2 页**（D-14） | 提前渲染即将进入视口的页 | 翻页边界不再才开始渲染 |
| **160ms 预览窗口**（D-18）+ 旧内容顶替（D-12/D-19） | 连续缩放期间不提交渲染，只显示旧内容 | 一串滚轮只渲染**最终那一档**，而不是每档都渲染 |

**关键结论（容易被忽略）**：因为瓦片是按"位图像素"切的，而当前缩放下位图像素 = 内容单位，
所以**视口覆盖的瓦片数几乎与缩放无关**（都是 6–9 块）。
也就是说，"像素工作量随缩放平方增长"这件事，**分块已经解决掉了**。
下面两条路线要解决的是**另外两件事**：
"手势过程中的观感"（阶梯）与"请求模型本身的耦合/调用开销"（视口空间）。

---

## 1. 预览质量阶梯（preview quality ladder）

### 目标
手势进行中（滚轮连续缩放、慢速触控板捏合）**主动渲染一张便宜的、但内容正确的图**，
手势结束后再补全清晰图。用户看到的是"先糊后清"，而不是"先是旧图、再突然清晰"。

### 机制
把"质量"变成渲染键的一个维度，预先定义几档（阶梯）：

```text
Full       = 目标缩放（例如 800%）
Preview/2  = 目标的一半（400%）
Preview/4  = 目标的四分之一（200%）
贴合档     = min(缩放, 视口宽 / 页宽)   ← 让"整页恰好铺满窗口"的档位，成本 ≈ 1 屏像素
```

* 手势期间只请求**贴合档**（成本与缩放无关，≈ 一屏像素）；
* 手势停止（例如 120–200ms 无输入）后请求 **Full**；
* 每一档都是正常的缓存条目，因此**回到之前看过的档位是瞬时的**（不会重渲染）。

### 与现状的差距（我们已经有的 / 还缺的）

| 已有 | 还缺 |
| --- | --- |
| 160ms 窗口内不提交渲染（省掉中间档） | 窗口内**不主动渲染任何东西**，只能显示**上一档的旧图** |
| 旧整页图 / 旧瓦片拉伸顶替（新区域可能没有旧图 → 白纸） | 没有"贴合档"这种**便宜且内容正确**的预览 |
| 缓存键含 `scale`（天然支持多档共存） | 没有"质量"概念：请求哪一档完全由缩放决定，会话不做策略 |

**一个具体例子**：慢速捏合缩放持续 1 秒、跨 6 个档位。
今天：全程显示"最初那一档的旧图"（一小时前的视野内容），直到停手才更新。
有了阶梯：每帧请求"贴合档"（约 1 块瓦片，~9ms），于是**手势过程中画面一直跟着变**。

### 代价与风险
* 接口层要动一点：`RenderKey` 增加质量维度，或由会话维护"当前目标档 / 预览档"两个比例；
* 缓存里同时存在两代内容（显存增加，但预览档很便宜）；
* 需要一条"何时算手势结束"的策略（定时器已有，`ZOOM_PREVIEW_WINDOW` 就是雏形）。

### 预期收益（数字）
* 手势期间每次更新从"等待 ~54ms（6 块瓦片）"降到"~9ms（1 块）"，
  并且在慢速捏合下**画面持续跟随**而不是冻结在旧图；
* 首次进入一页/新区域时不再白纸——先出贴合档，几百毫秒后变清晰。

**性价比：高。** 主要改动在 app + 会话策略，后端与 trait 基本不动。

## 2. 视口空间渲染（viewport-space rendering）

### 目标
让请求的含义从"**某一页在某个缩放下**"变成"**屏幕上这一块区域，按这个像素密度**"。
于是"渲染多少像素"由**窗口大小**决定，而不是由缩放决定：

```text
现在：请求 = 页 P @ 缩放 8  →  隐含 31 MP 的页面坐标系
改成：请求 = 内容区域 R（屏幕可见部分）@ 密度 D（设备像素/内容单位）
      渲染像素 = R 的屏幕尺寸 ≈ 窗口大小 = 1 MP（与缩放无关）
```

### 机制
```rust
struct RenderRequest {
    page: PageIndex,
    region: Rect,        // 内容空间中的可见区域（或对齐到内容网格的块）
    density: f32,        // 设备像素 / 内容单位（= pixels_per_point × 目标质量）
    rotation: Rotation,
}
```
后端把 `region` 反算成页面坐标，用**一个变换矩阵**直接渲染到窗口大小的位图
（`FPDF_RenderPageBitmapWithMatrix` 支持这种做法；pdfium-render 有 `set_matrix`/`translate` 等封装）。
缓存键随之变成 `(page, region 的对齐网格坐标, density, rotation)`。

### 与"分块渲染"的诚实对比

视口空间渲染**不是**"分块做不了的事"，而是同一目标下更干净的模型：

| 维度 | 分块（现状） | 视口空间 |
| --- | --- | --- |
| 像素工作量 | 已限定在视口 6–9 块 ≈ 1.6 MP ✅ | 同样 ≈ 1 MP ✅（**打平**） |
| 后端调用次数 | 每块一次（复杂页每次都要重新走内容流） | 一块区域一次，调用更少 |
| 请求里出现的"整页像素尺寸" | 仍有 `set_fixed_size(4896×6336)`：虽然只画一块，但语义上仍指向 31 MP 的坐标系 | 完全不存在大尺寸概念 → 消灭"纹理/内存上限"这一类问题 |
| 分辨率与缩放的关系 | 绑死（`scale = 缩放`）→ HiDPI 变糊、阶梯需要额外概念 | 解耦（`density` 独立）→ HiDPI、阶梯、降采样都自然 |
| 极端缩放的路径渲染成本 | 以巨大比例重绘矢量（细线/虚线可能更贵） | 按设备像素密度重绘，成本稳定 |

**所以真正的收益是**：把"缩放"从渲染参数里拿掉，换来 ①HiDPI 清晰度、②质量阶梯、
③更少的调用与大尺寸语义的消失。**而不是**"分块不够快"。

### 代价与风险
* **接口层改动**：`RenderRequest` / `RenderKey` / `PageRaster` 的语义、会话的瓦片逻辑、
  两个后端实现、以及一大票测试都要跟着改 —— 这是本项目里"最贵"的一类改动
  （按你最初的规则：**先出设计、评审通过再写代码**）；
* 平铺对齐：区域要按内容空间的网格对齐，否则**滚动时每帧都会产生新键**、缓存命中率归零；
* 旋转/页面尺寸差异、超大页、扫描件（位图内嵌）等边界都要重新验证。

### 预期收益（数字）
* 800% 时：从"6 块瓦片 × ~9ms ≈ 54ms + 6 次调用"变成"1 次调用、约 1 MP"；
* 复杂页面（扫描件、密集矢量）收益更大，因为每次调用的内容流开销被摊薄；
* 彻底消除 800% 那一类"大尺寸引发的问题"（我们为此绕了一圈：D-17/D-21）。

**性价比：中。** 收益真实但**部分已被分块拿到**，改动面却最大。

## 3. 关系、顺序与判据

* 两者**正交**：阶梯是"**策略**"（什么时候请求哪一档），视口空间是"**模型**"（一档请求是什么）；
* 阶梯可以**在现有接口上**实现（键里加质量维度即可），视口空间则必须动接口；
* 建议顺序：**① 阶梯 → ② 屏幕空间预取（按滚动方向 prioritise 瓦片）→ ③ 视口空间渲染**；
* 判断值不值得做 ③ 的方法：
  1. 用 `PDF_READER_DIAGNOSE=1` 记下打开**一份真实的重文档**（扫描件或图多的页）时的
     `画法=瓦片 n/m` 与手感；
  2. 若"单块瓦片耗时"远高于实测的 ~9ms（例如 50–200ms），说明瓶颈在**每次调用的内容流开销**，
     ③ 的收益最大；
  3. 若单块仍在 10ms 量级，先做 ① 就足够，③ 可以继续压后。

（现有诊断已打印每页画法与瓦片就绪数；若要支撑上面的判据，可以再加"最近一批渲染的耗时"，
属于 ① 或 ③ 实现时顺手加的小改动。）
