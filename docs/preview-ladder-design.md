# 预渲染阶梯（preview ladder）设计 —— 待评审

> 状态：**设计草案，未写代码**（按项目规则：先设计、评审通过再实现）。
> 相关：D-12（旧图顶替）、D-15（分块阈值 4 MP）、D-18（160ms 预览窗口）、D-19（纹理保留）。
> 背景讨论见 [deep-zoom-design.md](deep-zoom-design.md) §1。

---

## 0. 一句话结论

**"质量档"其实就是"更小的 `scale`"** —— 而 `RenderKey` 已经按 `scale_milli` 分键、
缓存也天然支持同页多档共存。所以本设计**不需要改 `RenderKey`、不改 `RenderCache`、
不改 `PageRaster`/后端**，只需要在会话里加一个"当前该请求哪一档"的策略，外加两个查询方法。

---

## 1. 目标 / 非目标

### 目标
1. **手势期间画面持续跟随**：连续缩放（滚轮/捏合）中，画面跟着变，而不是冻结在旧图；
2. **新区域不再白纸**：手势中进入视野的内容也能立刻有（低清）画面；
3. 手势结束后**尽快出清晰图**，且中间的过渡不闪白（沿用 D-12/D-19）。

### 非目标
* 不改渲染模型（不引入"内容区域 + 像素密度"，那是已搁置的视口空间渲染）；
* 不处理滚动型手势（翻页/滚动已由预取 ±2 页 + 每帧限量上传覆盖）；
* 不做"手势中降采样滚动"之类更激进的策略。

---

## 2. 关键洞察：为什么这次改动很小

| 事实 | 含义 |
| --- | --- |
| `RenderKey { page, scale_milli, rotation, tile }` 已含 `scale_milli` | 不同质量档天然是**不同键**，互不冲突 |
| `RenderCache` 存的是"键 → 位图" | 多档共存**无需改动** |
| app 的绘制已有"当前档没有就用**最接近的旧档**拉伸"（D-12） | 预览图会被**自动**找到并放大显示，绘制代码几乎不用改 |
| `KeyedStore::retain_preview_scales` 保留「当前比例 + 最接近的另一个比例」 | 预览档会被**自动**保留，不会被裁掉 |
| `request_page` 现在无条件用 `placement.scale` | **这是唯一需要改的地方**：预览模式下改用"预览档" |

## 3. 接口改动（pdfcore）

### 3.1 新增质量枚举

```rust
/// 渲染质量档位。语义：**完整** 用布局当前比例；**预览** 用一个更便宜的比例。
#[derive(Debug, Clone, Copy, PartialEq, Eq, Default)]
pub enum RenderQuality {
    /// 完整质量（默认）：按 `PagePlacement::scale` 渲染。
    #[default]
    Full,
    /// 预览质量：按"预览档"渲染（更小、更便宜，画面稍糊）。
    Preview,
}
```

### 3.2 新增命令

```rust
pub enum ViewerCommand {
    // ...
    /// 切换渲染质量（UI 在手势开始/结束时发送）。
    SetRenderQuality(RenderQuality),
}
```

`SessionState` 增加 `pub render_quality: RenderQuality`，并在切换时：
* 切到 `Preview`：**取消**当前可见页上"完整质量"的在飞任务（它们注定被浪费）；
* 切到 `Full`：不做特殊处理，下一帧正常 `RequestVisible` 即会请求完整质量。

### 3.3 预览档的计算（阶梯量化）

```rust
/// 预览档 = 目标缩放 ÷ 除数，再**量化到 2 的幂**，并夹取到上下限。
pub const PREVIEW_DIVISOR: f32 = 4.0;
pub const PREVIEW_SCALE_MIN: f32 = 0.25;

fn preview_scale(&self, page: PageIndex) -> Option<Scale> { /* 见下 */ }
```

* **除以 4**：预览像素数是完整档的 1/16，成本与内存都掉一个数量级；
* **量化到 2 的幂**（0.25 / 0.5 / 1 / 2 / 4…）：连续滚轮跨 10 档时，
  预览档只会命中 2–3 个不同的键 → 会话的"同键去重"直接生效，**不会为每个中间档都渲染一次**；
* **只在与完整档差距 ≥ 2 倍时才启用**：差距不足时预览没有意义（照样贵），直接按完整档走。

### 3.4 新增两个查询（app 需要知道"这一档"是什么）

```rust
impl DocumentSession {
    /// 某页**当前实际会请求**的比例（预览模式下是预览档，否则是布局比例）。
    pub fn render_scale(&self, page: PageIndex) -> Option<Scale>;

    /// 按**具体比例**取位图（`image_for` 是按"布局比例"取，预览档取不到）。
    pub fn image_at(&self, page: PageIndex, scale: Scale) -> Option<Arc<RasterImage>>;
}
```

`image_for(page)` 保持原语义（= `image_at(page, placement.scale)`），调用方不受影响。

### 3.5 请求路径

`request_page` 里把 `placement.scale` 换成 `self.render_scale(page)`，
其余（是否分块、提交、去重、取消）**完全复用**：

```rust
fn request_page(&mut self, page: PageIndex, priority: RenderPriority) {
    let Some(placement) = self.layout.placement(page).copied() else { return };
    let Some(scale) = self.render_scale(page) else { return };
    let pixel_size = /* 用 scale 算出的像素尺寸 */;
    if self.tiling.requires_tiling(pixel_size) {
        self.request_tiles(placement, scale, priority);   // 预览档若仍很大，同样会分块
    } else {
        self.submit(/* 整页 @ scale */, RenderKey::new(page, scale, placement.rotation));
    }
}
```

> 注：预览档通常是"整页一张小图"（面积是完整档的 1/16，一般已低于 4 MP 阈值），
> 因此手势中实际是**一次廉价渲染覆盖整页** —— 顺带解决了"手势中滚动到新区域是白纸"。

## 4. 时序（含数字，612×792 页 / 视口约 840×800）

| 场景 | 今天 | 采用阶梯后 |
| --- | --- | --- |
| 滚轮从 100%→800%（10 档，约 300ms） | 160ms 窗口内不提交；窗口过后渲染完整档（800%：6 块瓦片 ≈ 6×9ms ≈ 54ms）；期间只看旧图 | 每档请求预览档（2 的幂：2→2→4→4…），**去重后实际渲染 2 次**（scale 2 与 4）；每次整页约 1.9 MP / 7.6 MB；画面持续跟随 |
| 慢速捏合 1 秒跨 6 档 | 全程冻结在最初那一档的旧图 | 预览档随档位变化，画面一直跟着变 |
| 手势停止 | 下一帧请求完整档 | 同（预览图继续显示，直到完整档到齐） |
| 手势中滚到相邻页（新区域） | 无旧图 → 白纸 | 预览档覆盖整页 → 有内容 |
| 800% 时静置 | 6 块瓦片，清晰 | 同（预览被完整档替换） |

各档预览成本（估算，实施时用诊断实测校准）：

| 目标缩放 | 完整档 | 预览档（÷4，量化） | 预览像素 / 内存 |
| --- | --- | --- | --- |
| 800% | 分块 6×512² ≈ 1.6 MP，≈54ms（实测 9ms/块） | scale 2.0 | 1.9 MP / 7.6 MB |
| 400% | 分块 ≈4 块 ≈ 1 MP，≈36ms | scale 1.0 | 0.5 MP / 2 MB |
| 200% | 整页 1.9 MP（< 4 MP，不分块） | 差距不足 2 倍 → 不启用 | — |
| 100% | 整页 0.5 MP | 不启用 | — |

**结论**：阶梯只在"完整档明显更贵"时启用（本方案里即 ≥ 200% 左右），
低倍下行为与今天完全一致。

## 5. 与既有机制的关系

| 机制 | 变化 |
| --- | --- |
| D-18 的 160ms 窗口 | **语义调整**：窗口内从"不提交任何渲染"改为"提交**预览档**渲染"。窗口本身仍用于判断"手势是否结束"（结束时切回 `Full`） |
| D-12 旧图/旧瓦片顶替 | 保留不动。预览档本身就是"最接近的旧档"，会被自动找到并放大显示 |
| D-19 纹理保留 | 保留不动（"当前 + 最接近的另一个比例"刚好覆盖预览档） |
| D-14 预取 ±2 页 | 保留不动。预取仍按**完整档**（用户停手后马上要看的那一档）—— 需要明确：预取用完整档，避免"预取了一堆糊图" |
| D-10/D-13/D-17/D-20/D-21 | 无关，不受影响 |
| 后端（PDFium 适配层） | **完全不动** |

## 6. 资源、风险与回退

* **显存**：预览档每页一张小图（800% 时 7.6 MB/页），加上完整档瓦片（约 6 MB/页），量级可控；
  纹理裁剪策略已把"每页两档"设为上限。
* **PDFium 串行**：预览请求与完整请求共用一条队列。切到预览时会取消完整档的在飞任务，
  因此**不会出现"排队等完整档渲染完才轮到预览"**的情况。
* **抖动风险**：手势持续时间很短时，可能"预览刚出来就切回完整档"。
  缓解：切回 `Full` 时**不取消**已完成的预览（它本来就是缓存内容，直接被复用）。
* **回退开关**：预览除数与"最小启用比例"做成常量；若不满意，把 `PREVIEW_DIVISOR` 设为 1.0
  即等于关闭阶梯（行为回到今天）。
* **不做的事**：不改 `RenderKey`/`RenderCache`/`PageRaster` 语义，因此**不存在接口破坏**，
  两个后端实现与既有 100+ 测试不受影响。

## 7. 测试计划

**进入 `cargo test`（逻辑层）**
1. `RenderQuality` 默认值 = `Full`；`SetRenderQuality` 幂等；
2. 预览档计算：800%→2.0、400%→1.0、200%→不启用、100%→不启用、超大页 → 仍分块；
3. 预览档**量化到 2 的幂**：连续 10 档只产生 2–3 个不同键（断言键集合大小）；
4. 切到 `Preview` 会取消该页完整档的在飞任务（断言不再产出完整档的 `PageRendered`）；
5. `render_scale` / `image_at` 与 `image_for` 的一致性（`Full` 模式下三者等价）；
6. 预取仍使用完整档（断言预取键的比例）。

**必须由你人工验收（agent.md 规则 2）**
* 慢速捏合/连续滚轮时画面是否**持续跟随**（不再冻结在旧图）；
* 手势中滚到相邻页是否不再白纸；
* 停手后清晰图出现的延迟是否可接受；
* 预览档的模糊程度是否可接受（这是 K 值的取舍）。

**实施时顺手补**：诊断行增加 `质量=预览/完整` 与"最近一批渲染耗时"，
以便用你的真实重文档校准 K 与量化档。

## 9. 待你决定的 4 个问题

1. **预览除数 K = 4？** 预览像素 = 完整档的 1/K²。K=4 → 1/16（糊但极快，推荐）；
   K=2 → 1/4（清楚些但仍明显省，代价是每次预览约 4 倍时间）。
2. **预览档量化到 2 的幂（0.25/0.5/1/2/4）？** 推荐是：连续缩放才不会为每个中间档各渲染一次。
3. **只在完整档 ≥ 200%（即差距 ≥ 2 倍）时启用？** 推荐是：低倍下全清晰本来就只要几毫秒，
   强行降质没有意义。
4. **手势结束判定沿用 160ms？** 推荐是；若你觉得"清晰图来得慢"，可以降到 100ms
   （代价是快速连续操作时可能多渲染一次完整档）。
