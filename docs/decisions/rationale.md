# 架构说明：为什么现在是这样

> 按主题讲**当前设计的关键理由与取舍**；每条给出"结论 / 理由 / 代价 / 何时该重新考虑"。
> 结构事实见 [`../current/architecture.md`](../current/architecture.md)，机制细节见
> [`../current/rendering.md`](../current/rendering.md)，决策 ID 查 [`log.md`](log.md)。

## 1. 为什么接口层零依赖、且只用 trait 装配

**结论**：`pdfcore` 只依赖 std，把后端（PDFium）、缓存、调度、布局、选区全部做成 trait，
由 `DocumentSession::new` 注入。

**理由**：这类程序最容易死于"渲染、缓存、UI 状态搅在一起"，一旦搅在一起，任何
"白块/错位/卡顿"都要在真机上猜。把可判定部分（几何、布局、调度、选区）压进纯逻辑层后，
它们可以在毫秒级单测里验证；`testkit` 的假后端就是这条路走通的证据（`tests/assemble.rs`
在没有 PDFium、没有 GPU 的环境里跑通全链路）。

**代价**：多一层间接（`Arc<dyn …>`）；trait 变更会波及三处（接口、实现、测试替身）。

**何时重新考虑**：只有当某个 trait 的实现成为唯一可能（例如放弃可替换后端）时才值得收敛。

## 2. 为什么有四个坐标系，且只有 `PagePlacement` 做换算

**结论**：PDF 页面空间（左下原点、y 向上、point）→ 内容空间（文档左上、y 向下）→ 视图空间
（减滚动）→ 渲染像素（块位图）。换算只在 `PagePlacement`（以及块的 `TileGrid`）里发生。

**理由**：历史上最顽固的两类 bug 都是坐标混用——"高亮/链接框整体偏移"（D-27 归一化）、
"748% 时瓦片被压进页面左上角、满屏全黑"（D-17）。把换算收到一处，再配往返测试，
才能让"错位"变成可判定的问题。

**代价**：所有 UI 代码必须经过 `placement`，不能"顺手加个偏移"；多一点函数调用。

**何时重新考虑**：不需要。这是硬约束（INV-1/INV-2）。

## 3. 为什么分块、为什么是"2 的幂网格 + 512px 目标边长"

**结论**：页的渲染像素面积 > 4 MP 才分块；分块时用 `TileGrid`（每边 2 的幂，块边长尽量接近
512px，边界 `round(i·total/side)` 共享）。

**理由**：4 MP 以上整页位图的内存与耗时随面积线性增长（31 MP = 124 MB），而单块约 9ms
（实测）——分块既省内存也更跟手（D-15）。共享整数边界让相邻块**严格相接**，
不需要"重叠一像素"这种补丁（D-90）。

**代价**：块多了以后"画法"成了独立问题（见 §5）；`TilingPolicy` 的阈值是个固定数而不是预算。

**何时重新考虑**：出现"块太多导致请求碎片化"的实测（每屏上百块），或整页位图的预算变化。

## 4. 为什么用波段（超采样）而不是"每次缩放都重渲染"

**结论**：渲染比例取 `1.6^(band+1)`（波段上界），同一波段内任意缩放共用一次渲染；
键里存的是**渲染比例**，所以波段内缩放既不重渲染、也不取消在飞任务。

**理由**：连续缩放会产生一串中间比例（100→120→140→150），逐个渲染既浪费又每步掉帧（D-18）；
而"只下采样"（`u ≤ 1`）保证缩放过程中不会把位图放大变糊（D-91）。

**代价**：整页位图最多是显示面积的 2.56 倍；跨波段时要有"旧内容顶住"的策略（§5）。

**何时重新考虑**：内存紧张到需要更小的 `overscan`（如 1.25）时——但会牺牲清晰度上限。

## 5. 为什么画法要"整页级降级"，而不是缺哪块补哪块

**结论**：一页每帧只选一个来源：当前波段的整页图 / 旧整页图 / 旧波段块 / 当前波段块。
缺块时先铺**整页底料**（覆盖优先），再叠当前波段的块；**不逐块混用不同比例**。

**理由**：这是本项目最贵的教训。D-87 试过"缺块处用旧比例同块拉伸顶上"，结果是相邻块
各持一个比例、接缝变成**几何错位**，比白块更刺眼（D-88 回退）。之后的白块修复走了另一条路：
分层（底料 + 主图层），并加"可见范围全部就绪才切"的就绪门槛（D-97/98/99）。

**代价**：波段切换时整屏会先糊一下再变清晰（用户已确认可接受）；需要 400ms 超时兜底，
否则某块渲染失败会让页面永远停在糊图。

**何时重新考虑**：若将来能做到"按块渐进替换且视觉无接缝"（例如所有块都来自同一网格、
同一比例，只是分辨率不同），可以重新评估。

## 6. 为什么后端要"硬失败"而不是静默拉伸

**结论**：块请求携带**页面空间矩形 + 期望像素尺寸**；后端映射后校验三项（整像素、尺寸、
在页内），不符返回 `CoreError::Internal`。

**理由**：D-84/D-86 的症状是"画面有图，但同一行文字在接缝处错开 1/5 字高"——它是几何推导
不一致的**表象**，静默拉伸只会让人继续往错的方向查。硬失败把"错"变成一眼可见的错误
（D-95），而正确性由"块渲染 == 整页裁剪"的逐像素测试守住。

**代价**：几何一旦漂移，用户看到的是错误而不是"稍微歪一点"；需要更严的测试。

**何时重新考虑**：不需要。宁可报错。

## 7. 为什么有两级缓存（CPU 位图 + GPU 纹理）

**结论**：`LruCache`（512 MiB，按字节 LRU）管位图；`KeyedStore`（128 条目）管纹理，
每帧按"当前波段 + 最近其它波段 + 当前以下最近的整页波段"三档裁剪。

**理由**：位图与纹理的失效条件不同——位图按"有没有地方用"和内存淘汰；纹理受显存与上传
成本限制，而且缩放过渡需要"上一档"的底料（D-19），白块修复又需要"更低的整页图"当底料（D-97）。
两级各自管自己的资源，比重试一套统一策略简单。

**代价**：两套淘汰策略要一起调；纹理层按条目数限额，没有显存字节预算。

**何时重新考虑**：出现显存超预期（大页 + 多窗口）时，把纹理层也改成字节预算。

## 8. 为什么存档只存元数据，并记录"分辨率"

**结论**：`<pdf>.json` 只存页号 / 页面空间矩形 / 正文尺寸 / 题目或文字 / **截图时的显示比例**
（v2），像素不入档；预览图按记录的分辨率请求渲染后合成。

**理由**：像素入档会让文件膨胀、且与缩放绑死（D-64）。但"按当前缩放重建"会让预览依赖
"你此刻在哪儿"——高倍下没走过的地方就没像素（D-101 修的就是这个）。记录分辨率后，
预览的分辨率与当前缩放解耦。

**代价**：需要一套版本迁移规则（D-100）；存档仍会丢未知字段。

**何时重新考虑**：需要"存档自带高清预览、离线也能看"时（那时要考虑存档体积与压缩）。

## 9. 为什么 UI 的纯逻辑要抽到 `view.rs`

**结论**：坐标换算、输入映射、纹理存储、画法决策、快照拼合、浮窗几何全部放
`crates/app/src/view.rs`，`app.rs` 只做"读输入 → 调会话 → 画"。

**理由**：`app.rs` 需要真实窗口，无法自动验证；把能判定的部分抽出来后，它们能进单测
（现在 `view.rs` 有 60+ 用例，覆盖画法判据、快照、保留策略）。这条是"减少真机往返"的唯一
可持续办法。

**代价**：`view.rs` 本身也在变大（~2.9k 行）；有些逻辑需要"传引用而不是借用 self"，签名偏长。

**何时重新考虑**：`view.rs` 继续膨胀时，按职责再分文件（画法 / 快照 / 浮窗 / 保留策略）。

## 10. 为什么诊断用 stderr 而不是日志框架

**结论**：所有诊断是环境变量开关 + `eprintln!`，格式面向人眼比对。

**理由**：早期没有日志基础设施，`PDF_READER_DIAGNOSE=1` + 一行行数据是"真机问题唯一能拿到
的证据"，而且不需要引入依赖。事实证明它救过很多次（D-29 帧率、D-85 接缝、D-99 白块）。

**代价**：无级别、无落地文件、无结构化输出；不同前缀命名风格不统一；拖动过程中看不到。

**何时重新考虑**：下次再出现"某种现象只能在拖动时观察"时，改为带环形缓冲的诊断模块
（见 [`log.md`](log.md) 开放项 3）。
