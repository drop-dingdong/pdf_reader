# S7 评估：正文归注释、外部注释正文、去 `.annot.json`、保存器

> 状态：**评估完成，待确认顺序与持久化策略**（2026-10-28）。本文不改代码。
> 相关：S6 评估（[`s6-readback.md`](s6-readback.md)）、`docs/current/readback.md`、D-134～D-144。

## 1. 结论摘要

* **方向合理**：正文归注释、PDF 作为注释来源，都是正确目标；但**不建议按“外部注释正文 → 去 preview → 去
  annot.json → 保存器”的原顺序**做。
* 原顺序的两个问题：
  1. **外部注释正文**在当前模型里没有地方放正文，只能临时再造“外部注释的 preview 条目”，
     等下一步“正文归注释”时又全部推翻；
  2. **去 `.annot.json` 放在保存器之前**意味着“未写回的新注释”没有持久化载体；一旦软件崩溃/关闭，
     新注释和正文就丢了。保存器（或明确的自动写回策略）是去 overlay 的前置条件。
* 推荐顺序：**P1 正文归注释（保留 `.annot.json`）→ P2 外部注释正文读/编辑 → P3 保存器 → P4 去 `.annot.json`**。
* 需要先确认 3 个决策：去 overlay 后的保存时机、外部注释正文的编辑边界、`.annot.json` 的最终形态。

## 2. 现状（代码事实）

当前一条注释的数据分成三层：

| 层 | 存什么 | 位置 |
| --- | --- | --- |
| 注释几何 | id / page / kind / color / opacity / **body_title** | `<pdf>.annot.json` |
| 正文 | 以哨兵标题 `#annot:<id>` 存的 **CustomPreview**（Text） | `<pdf>.json` 的 `custom_texts` |
| PDF | 写回的 `/Contents`、`/NM`、几何、AP | `<pdf>` |

关键耦合：

* `Annotation` 没有 `body` 字段，只有 `body_title`；
* 新建注释时 `apply_edit(AddAnnotation)` **自动创建一条空正文 preview**（标题 `#annot:<id>`）；
* 点击注释打开的是这条 preview 的浮窗；正文编辑就是编辑 preview 的文本（失焦提交，
  **不进撤销栈**）；
* 预览列表里能看到这些正文条目；删除正文条目会让注释显示“正文已丢失”；
* 导出/写回时按 `body_title` 从 `custom_previews` 找正文；S6a 从 PDF 恢复正文时也是**造 preview 条目**；
* S5c 原地写入前会 `save_all()`，把 `.annot.json` 与 `.json` 都落盘；S6c 重建时会删掉
  `.json` 里 `#annot:` 条目，再从 PDF 正文重建。

因此现在“注释的正文”**依赖 preview 这个中间载体**，而且 `.annot.json` 与 `.json` 必须成对存在
才是完整状态。

## 3. 目标拆解

| 目标 | 内容 | 依赖 | 风险 |
| --- | --- | --- | --- |
| **G1 外部注释正文** | 读回其他阅读器的 `/Contents`，并能编辑（只改内容，不改几何） | 正文必须有地方放（G2） | 外部注释 id/只读语义、对象更新 |
| **G2 正文归注释** | `Annotation` 自带 `body`；正文不再用 CustomPreview 承载；不进预览列表 | 无（模型/持久化改造） | 迁移、正文编辑撤销、UI |
| **G3 对象级保存器** | 只追加真正变化的注释对象/页面对象（像 Okular） | 需要对象号与 ObjStm 处理 | 复杂、容易写坏 PDF |
| **G4 去 `.annot.json`** | PDF 成为注释唯一来源 | G2 + G3（或明确的自动写回策略） | **未保存数据会丢**、迁移/回滚 |

## 4. 逐项合理性

### G2（正文归注释）：应该先做，收益最大、风险最低

* 模型加 `body: Option<String>`，`body_title` 删除；`.annot.json` 升 v3（几何 + 正文），
  或先保留 v3 过渡；
* 新建注释不再创建 preview；预览列表不再出现 `#annot:` 条目；
* 正文编辑直接在注释浮窗里改 `Annotation.body`，加入 `AppEdit::SetBody`（可撤销）；
* 导出/写回/读回都从 `Annotation.body` 取，不再查 preview；
* 迁移：打开旧文件时把 `.json` 里 `#annot:<id>` 正文搬进注释，写 v3；
* 这一步**不改变 PDF 格式**，失败可回退到旧版本，风险可控。

### G1（外部注释正文）：应放在 G2 之后

* G1 需要：外部注释有 `origin = Pdf`/只读几何；正文从 `/Contents` 读进 `Annotation.body`；
  允许编辑正文（写回时 `SetStringValue("Contents")`），几何仍只读；
* 如果先做 G1，当前只能临时造 `#foreign:<id>` 的 preview 条目；G2 一做完这些又要拆掉，
  测试和迁移都要做两遍；
* 放在 G2 之后，外部注释与我们的注释共用 `body` 字段，G1 主要是“读 `/Contents` + 允许编辑 + 写回”三件事。

### G3（对象级保存器）：可以最后做，但它是 G4 的“质量前提”

* 现状（D-144）：同步逻辑已经能只处理变化的注释，但 **PDFium 的 `FPDF_INCREMENTAL` 仍整份追加**
  （实测无变化也 2979→4351 字节）；Okular 只追加一个对象。
* 要像 Okular 只写变化对象，需要自己写增量更新：
  * 我们已经能解析直接对象、页面 `/Annots`、xref/trailer（`pdf_repair`）；
  * 难点是 **对象号**：`FPDFAnnot` 不暴露对象号；Adobe 的注释在 ObjStm 里，直接扫描看不到；
  * 需要评估：解析 ObjStm / xref stream，或对“我们自己的注释”用自定义对象、对外部注释退回 PDFium。
* 不做 G3 也能做 G4（用 PDFium 增量 + 显式保存），代价是文件增长快、保存慢；
  但若 G4 要求“每次编辑自动写回”，G3 基本是必须的。

### G4（去 `.annot.json`）：合理，但必须定义“未保存状态”

去掉 `.annot.json` 后，**新加但还没写进 PDF 的注释住在哪里？** 三种策略：

| 策略 | 行为 | 代价 |
| --- | --- | --- |
| **A. 自动写回** | 每次增删/改正文 → 立即增量写 PDF | 需要 G3；每个笔画都写盘；撤销要写反向操作 |
| **B. 显式保存** | 编辑只在内存；点「写入 PDF」才落盘 | 关闭/崩溃丢失未保存注释；需要明确提示 |
| **C. 保留日志** | 用一个小 journal/临时 overlay 做崩溃恢复 | 实际上仍是 sidecar，和“完全去掉”目标冲突 |

推荐先做 **B**（显式保存）作为过渡，等 G3 稳定再评估 A；**不建议在 G3 之前直接 A**。
另外需要决定：打开时 PDF 是唯一来源后，`.json` 里旧的 `#annot:` 正文如何迁移、是否保留备份、
`annot.json` 是否删除/重命名。

## 5. 为什么建议调整原顺序

原顺序：**G1 → G2 → G3**（然后 G4）。

* G1 的价值要等 G2 才完整；先做会造一套临时正文存储，随后删除；
* G3 放最后意味着 G4 在 G3 之前，未保存数据没有载体；
* 调整后：**G2（模型）→ G1（复用模型）→ G3（保存质量）→ G4（去 overlay）**，
  每一步都能独立验收、可回退。

如果坚持原顺序，也可以做，但需要接受：
1. 外部注释正文会先存在 preview（或临时 map）里，G2 时再迁移一次；
2. G4 之前必须有“显式保存 + 明确丢失风险”的 UX，否则数据会丢；
3. G3 之前文件增长明显（PDFium 保存器）。

## 6. 建议的阶段计划（下一步细化）

* **P1 正文归注释**（保留 `.annot.json` v3）
  * 模型/持久化/迁移；去掉 `#annot:` preview；注释浮窗内的正文编辑 + 撤销；导出/读回/写回改用 `body`；
  * 验收：旧文件打开后正文在、预览列表不再有注释正文条目、撤销正文编辑、写回 PDF 正文正确。
* **P2 外部注释正文**
  * `origin`/只读几何；读 `/Contents` 进 `body`；允许改正文；写回时更新外部注释的 `/Contents`；
  * 外部注释不能删/改几何；用 fixtures 做回归；
  * 验收：Okular/Adobe 样本的正文可读、可改、写回后 Okular 能看到。
* **P3 对象级保存器**
  * 评估并实现“只追加变化对象”；ObjStm/对象号方案；保留 PDFium 作为兜底；
  * 验收：内容编辑只追加一个对象；文件增长接近 Okular；外部注释不被破坏。
* **P4 去 `.annot.json`**
  * 先按“显式保存”策略；打开时 PDF 为唯一来源；旧 overlay/`.json` 正文迁移与备份；
  * 再评估自动写回；
  * 验收：删掉 A/J 后可用；未保存退出有明确提示；写入失败可回滚。

## 7. 风险清单

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 去 overlay 后未保存数据丢失 | 高 | 先显式保存 + 提示；G3 后再自动写回 |
| 旧 `.json` 正文迁移遗漏 | 中 | 迁移前备份、逐条校验；保留只读旧文件 |
| 正文编辑没有撤销 | 中 | G2 加 `AppEdit::SetBody` |
| 外部注释正文写回失败 | 中 | 内容更新失败就回退到替换对象；写前备份 |
| ObjStm 里的对象号拿不到 | 高（G3） | 解析 ObjStm/xref stream，或对外部注释保留 PDFium 兜底 |
| 自动写回性能/卡顿 | 中 | 合并写入、后台任务、每笔延迟写 |
| 与外部阅读器并发修改 | 中 | 打开时快照 + 写前重新读；冲突提示 |

## 8. 需要确认的决策

1. **顺序**：接受“正文归注释 → 外部正文 → 保存器 → 去 overlay”的调整，还是坚持原顺序？
2. **去 overlay 后的保存策略**：显式保存（推荐过渡）/ 自动写回 / 保留 journal？
3. **外部注释边界**：只允许改正文（推荐），还是也要改颜色/几何（会变成“收养”外部注释）？
4. **`.annot.json` 的最终形态**：彻底删除 / 保留为可选缓存 / 迁移后只读备份？

## 9. 决策后的修订（2026-10-28）

用户确认/补充后，原分析需要修正的地方：

### 9.1 浮动对象：注释正文是独立的一类

用户提出的模型比“继续用 CustomPreview”更干净：

* 浮窗可以有多种来源：**注释**、自定义文字/图片 preview、链接预览；
* 注释解析后得到一个“类文字预览”的对象，但**不是** CustomPreview：
  * 只由注释触发，不出现在侧栏；
  * 不写进 `.json`；
  * 正文直接属于注释（`Annotation.body`）。
* 实现上把 `Float` 的来源从 `custom: Option<usize>` 改成枚举，例如：

  ```rust
  enum FloatOwner {
      Annotation(AnnotationId),
      CustomPreview(usize),
      // 链接预览等以后需要时再加
  }
  ```

* 正文编辑只有在 owner 是 `Annotation` 时才写回注释，并进入撤销栈（`AppEdit::SetBody`）；
  链接/自定义 preview 的编辑路径保持不变。
* 这样 G2 的“正文归注释”与 G1 的“外部注释正文”共用同一条浮窗/编辑路径，不需要任何临时 preview。

### 9.2 未保存状态：显式保存，默认丢弃

* 用户确认：**自动写回代价太大，显式保存合理**；
* 新加但尚未写进 PDF 的注释：**关闭阅读器或切换文件时默认放弃**；
* 不保留 journal（现在 app 状态本身也还没记录，等以后统一做脏位提示）；
* 这意味着 G4 之后：
  * `保存` 必须能**写 PDF**（不能只写 `.annot.json`，因为它已经没了）；
  * 状态栏/按钮需要明确“未保存”的提示（可以和其他自定义数据的脏位一起做）；
  * 写入失败时不能悄悄丢弃内存状态；应保留并提示，直到用户关闭/切换。

### 9.3 外部注释：只做“正文 + 删除”

用户明确当前阅读器只有“新建/删除”两种操作，因此外部注释的范围是：

* **读**：`/Contents` 显示在注释浮窗里；
* **改**：只改正文；几何/颜色仍然只读；
* **删**：允许删除外部注释（这是原评估漏掉的一条）。
* 不做“收养外部注释”“改颜色/几何”。

新问题（原分析未覆盖）：

1. **身份**：外部注释没有 `pd-fr:` id，删除/改正文时要在写回阶段重新找到它。
   方案：优先用 `/NM`（Okular 的 `okular-{uuid}`），没有就用
   `(页, 子类型, Rect, QuadPoints/InkList 指纹, 原正文)`；匹配不到或匹配到多条时**拒绝**并提示，
   绝不乱删。
2. **Popup 子注释**：高亮/文字标记可能带 `/Popup` 子注释；删除父注释时要同时删掉
   `FPDFAnnot_GetLinkedAnnot(annot, "Popup")` 指向的子注释，避免留下孤儿。
3. **持久化**：外部注释的正文修改/删除只存在于内存，**不写入 `.json`/`.annot.json`**；
   只有「写入 PDF」才落盘；未保存关闭则丢弃（与 9.2 一致）。

### 9.4 顺序再调整：去 overlay 可以早于“对象级保存器”

显式保存 + 未保存丢弃的语义确定后，G3 不再是 G4 的硬前置：

* G4 的 `保存` 可以用**现在的 PDFium 增量保存**（文件会变大，但正确）；
* 对象级保存器（G3）变成之后的**优化**，不是正确性前提；
* 因此推荐顺序变为：

  **P1 正文归注释 → P2 外部正文/删除 → P3 去 `.annot.json` → P4 对象级保存器**。

这更符合用户“保存器最后改”的意图，同时保留可回退性。

## 10. 修订后的阶段计划（待确认后细化）

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| **P1 正文归注释** | `Annotation.body`；`FloatOwner`；正文编辑进撤销栈；A 升 v3（几何 + 正文）；迁移 `.json` 里 `#annot:`；预览列表不再出现注释正文 | 旧文件正文不丢；列表无 `#annot:`；撤销正文；导出/读回正文正确 |
| **P2 外部正文/删除** | `origin=Pdf`、只读几何；读 `/Contents`；改正文；删除（含 Popup）；身份匹配失败拒绝 | Okular/Adobe 样本正文可读可改可删；写回后 Okular 验证 |
| **P3 去 `.annot.json`** | 打开时 PDF 为唯一来源；保存 = 写 PDF + `.json`；未保存关闭丢注释；备份/失败保留 | 删 A 后正常；未保存退出有提示；写入失败不丢内存 |
| **P4 对象级保存器** | 只追加变化对象（内容/删除/新增）；ObjStm/对象号方案；PDFium 兜底 | 内容编辑只追加一个对象；增长接近 Okular；外部注释不破坏 |

## 11. 修订后新增的风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 外部注释身份匹配失败/多条 | 误删/误改 | 拒绝并提示；写前重新读 |
| 删除父注释留下 Popup | 孤儿注释 | `GetLinkedAnnot("Popup")` 一并删 |
| 显式保存的未保存提示缺失 | 用户以为已保存 | 保存按钮/状态栏脏位（可与自定义数据一起做） |
| P3 后 `.json` 与 PDF 的保存顺序 | 一半成功一半失败 | 先写 PDF（备份+校验）再写 `.json`；失败保留内存 |
| 外部正文编辑在 A 仍存在时被误存 | 行为不一致 | P2 明确：外部编辑只由「写入 PDF」落盘 |

## 12. 结论（修订）

方向合理；用户对“浮动对象”的抽象和“显式保存/丢弃”的取舍让方案更简单、风险更可控。
调整后的顺序为 **P1 → P2 → P3 → P4**，其中 P4 从“正确性前提”降级为“性能/体积优化”。
下一步应把 P1/P2 写成可执行计划（字段、迁移、UI、测试），再开始改代码。
