# 演进史与教训

> 按阶段记录**怎么变来的**：改了什么、为什么、踩了什么坑、留下什么规则。
> 详细决策见 [`log.md`](log.md)，机制现状见 [`../current/`](../current/)。

## 阶段 1：契约与骨架（v1 → v3）

* 先定 9 个 trait、零依赖接口层、坐标系与"旋转先于缩放"，再写后端与 UI（D-00a…D-00f）。
* 补齐批量页几何（D-01）、分块（D-02）、锚点（D-05）、导航预解析（D-08）。
* 这一阶段的主要产出不是功能，而是**可测试的边界**：几何、布局、选区、调度都能脱离
  PDF 与 GPU 验证。

**教训**：接口先行的收益要到"改一次实现"时才显出来——`testkit` 让后来每一次渲染改造都能
先在内存在假后端上跑通，再上真机。

## 阶段 2：五轮人工验收（UI 层密集修补）

`docs/feedback-round-1..5.md`（已移入 git 历史）记录了这段时间。典型问题与结论：

| 现象 | 根因 | 留下的规则 |
| --- | --- | --- |
| 缩小时页面往左上漂 / 跳页位置不对 | 滚动夹取与跳页语义混用 | 逐轴夹取、内容小于视口时居中（D-09）；跳页=顶部对齐（D-11） |
| `Ctrl`+`+` 同时放大界面与页面 | egui 内建缩放与文档缩放冲突 | 关掉 `zoom_with_keyboard`，`Ctrl` 只作用于文档（D-10） |
| 拖动只有松手才动、且落后指针 | 命令延迟一帧 + 没持续 `request_repaint` | 拖动当帧生效（D-25/D-26），并持续请求重绘 |
| 200% 下每帧 300ms 全花在纹理 | 上传集合与裁剪集合不一致（上传完立即被丢） | 上传与裁剪共用 `texture_pages`（D-30） |
| 782ms 只画了 5 帧 | 一帧内做两遍逐像素转换 | 一遍完成 + 拖动期间暂缓上传（D-32），跟手优先（D-35） |
| 侧栏能拖但没图像 | 拖拽条参与布局流把画布高度吃光 | 显式矩形 + `interact`，画布保持满高（D-21） |
| 1292 个目录节点每帧布局 42ms | 非虚拟化 | 摊平 + `show_rows` 只看可见行（D-31） |
| 高亮/链接框整体偏移 | 文本坐标按 `MediaBox`、渲染按 `MediaBox ∩ CropBox` | 记录渲染盒原点并归一化（D-27） |

**教训**：这一阶段的 bug 几乎全是"UI 状态/时序"问题，而不是渲染正确性；它们的共同解法是
**把可判定的部分搬进纯逻辑 + 加诊断**，而不是在 `app.rs` 里打补丁。

## 阶段 3：浮窗、标注与截图（功能扩展期）

浮窗（D-36）、引用点（D-37）、截图（D-38/40/41）、悬停预览（D-43…D-48）、Pin 与侧栏
（D-49…D-59）、浮窗尺寸权威化（D-60/D-74）、存档（D-64…D-69）。

**教训（两条反复出现）**

1. **新出现的输入控件必须在当帧 `request_focus`**；`gained_focus()` 不能当判据（D-76/D-77）。
2. **"清理"必须排在"恢复"之前**，否则切换文档时刚读回来的数据会被清掉（D-68 → D-69）。

## 阶段 4：分块 v1（512 固定网格）

`TileSpec::grid_for/pixel_rect`、512 固定网格、`tiles_covering`。当时的问题：

* **800% 视野全黑**：`tile_view_rect` 写了 `pixels / scale`，瓦片被压进页面左上角（D-17）。
  定位靠诊断行"画法=瓦片 6/6 却全黑"。
* **接缝错位、同字画两遍**：同页混用多个比例的瓦片（D-86）。

结论：**缓存键必须包含"比例 + 块"**，**绘制必须只取当前比例**，**降级必须在整页层面**（D-88）。

## 阶段 5：波段 v2（D-90…D-95）

把"渲染比例"从"显示比例"里彻底拆出来：

* 纯几何 `pdfcore::tiling`（D-90）；波段与复用（D-91/D-92）；
* 渲染键/请求改用波段渲染比例、`TileGrid` 取代 512 网格、session/app 同步（D-94）；
* 后端改为"块页面矩形 + 期望像素尺寸 + 硬校验"（D-95）。

关键收获：**同一波段内改缩放不产生新的渲染请求**，键与贴图比例因此天然一致；
"块渲染 == 整页裁剪"可以逐像素验证（真实 PDFium，含奇数页宽与 `/Rotate 90°`）。

## 阶段 6：白块 v3（D-96…D-99）

错位消失后暴露出"白块"，修了三轮：

| 轮次 | 做法 | 结果 |
| --- | --- | --- |
| D-97 | 整页级就绪门槛（可见范围全齐才切）+ 三档保留（多留一档整页图） | 波段切换不再"几块清晰 + 大片白" |
| D-98 | 缺块处铺**整页底料**（覆盖优先），不再 `paint_blank` | 拖动方向的白块消失 |
| D-99 | 预览层也压在底料之上（分层而非二选一） | 修掉"连续放大时上一波段只画完一块就被取消 → 整屏只剩那一块" |

**教训**：
* "上一波段有没有画完"取决于用户是否在那一档停顿超过 160ms —— **不能假设旧内容完整**；
* 底料必须是**一张整页图**（单一比例、单一映射），才能既盖满又不产生几何错位；
* 每一轮都要能单提交回退，否则三次迭代会把代码搅成没人敢动的一团。

## 阶段 7：存档 v2 与预览图（D-100/D-101）

事实：预览图原先只从**当前波段**的缓存里取像素 → 换个缩放/位置就"只有走过的部分 + 白"，
甚至完全没有图。修法：

* 存档记录截图时的**显示比例**（v1 → v2 迁移，缺失按 100%，并置脏）；
* 预览图按记录分辨率**请求渲染**（`request_region` / `region_tiles`），在渲染像素里 1:1 拼图；
* 初次生成失败不再静默（`[预览]` 三类诊断）。

## 被推翻 / 回退过的做法（别再试一遍）

| 做法 | 为什么不行 | 结论来源 |
| --- | --- | --- |
| 质量"预渲染阶梯"（按缓存内容每帧推导档位） | 档位自激振荡 + 每次切档取消在飞任务 → 画面停止更新 | D-23 |
| 瓦片位置除以显示比例 | 748% 时瓦片被压进页面左上角 → 全屏黑 | D-17 |
| 同页混用多个比例的瓦片 | 接缝处内容比例不一致 → 错位、重影 | D-86 |
| 缺块处用旧比例同块拉伸顶上 | 相邻块各持一个比例 → 比白块更刺眼的错位 | D-87 → D-88 |
| 缓存键对显示比例做 1/8 量化 | 键里的比例 ≠ 真正渲染的比例 → 预览重建网格差几像素 | D-00f → D-94 |
| 瓦片缺失时只画"已缓存"的块 | 未就绪区域露出深色画布 → "视野全黑" | D-33 前身 |
| 每块缺失都描灰边 | 高倍下满屏网格线 | D-33 |
| 用 egui 内建 `resizable` 做侧栏 | 面板状态键挂在每帧变化的父 Ui 上，读不回来 | D-20 |
| 逐块判断"是新图还是旧图"来降级 | 把"缺图"换成"错位" | D-87 |

## 贯穿全程的教训

1. **先计划、后动刀**：D-93/D-96 两次先写计划（含判据表、测试清单、回退方式），
   再一次性实施 —— 这是本项目唯一稳定有效的"大改动"节奏。
2. **可回退粒度要小**：一次改动一个提交，能 `revert` 才算完成。
3. **先出诊断，再改逻辑**：白块能定位，全靠 `[画法]/[贴图]/[瓦片]` 三行数据；
   盲改绘制逻辑的结果在 D-84/D-87 出现过两次（都更糟）。
4. **不变量要写成测试**：`architecture.md` §7 那 11 条，每条都有对应的测试或结构约束。
5. **窗口相关的问题必须在用户机器上验证**：帧率、显存、真 PDF 的边界，逻辑层测不出来。
